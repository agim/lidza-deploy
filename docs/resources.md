# Application resources and server capacity

Open **Application → Resources** for CPU/RAM usage, effective container limits, restart counts, OOM state and the app's budget. **Servers → Manage server → Resources** shows live host capacity, apps and shared services. Advanced controls are optional. The Server health link also opens this page. Resource readings refresh about every ten seconds. Missing readings display Unavailable; interrupted connections retain the previous readings and show an error. Forms, row identities, focus and scroll remain stable during polling.

CPU 100% means one core, not the entire server. RAM usage is Docker's working-set measurement; file cache and swap are not included. Database sizes on Server health are disk sizes, not RAM. Shared databases/cache containers are listed separately and counted once. Retained services consume memory while running, but their maximum limits are not permanently reserved in automatic mode. Non-Lidza containers are reported but not controlled. Unbounded external workloads require sufficient host headroom; the agent cannot guarantee the behavior of software outside its ownership.

## Automatic capacity management (default)

Normal deployments do not require manual balancing of RAM reservations. The default is **automatic**, including saved policies from older releases that have no memory mode. Per-process and per-app limits remain enforced, but adding their maximums is not used to decide whether the host is full.

The agent reads Linux MemAvailable (including reclaimable cache) before admitting work. It protects host headroom and the helper pool, deducts the build cap while a build is starting/running, and accounts for concurrent pending launches that are not yet running. It does not reserve idle build capacity or count an already-running container as another launch. An existing healthy cache needs only an authenticated health check.

If actual memory headroom is temporarily insufficient, builds and container launches wait and recheck every five seconds for up to three minutes, bounded by the caller's cancellation/deadline. They resume without a user retry when memory becomes available. Genuine Docker/controller errors and invalid per-app limits are not retried as memory pressure. Backup/restore helpers also wait for their bounded pool and sufficient host headroom.

The overview shows live **RAM available** and **Available for new work**, rather than a negative total of configured maxima. CPU is distributed across running/launching apps; registered idle apps do not reduce active apps' shares. Polling preserves forms, focus, expanded controls and scroll.

Limits are ceilings, not peak-use guarantees. Automatic mode deliberately permits the sum of ceilings to exceed physical RAM; simultaneous peaks still require physical capacity. It preserves running RAM caps rather than shrinking or killing healthy apps to make a model fit. Unmanaged workloads remain outside the agent's control. For an operator who explicitly needs all maxima reserved in advance, **Advanced resource controls → Memory management → Strict reservations** retains that behavior. A strict shortfall blocks new work immediately and must be corrected explicitly.

## App limits

New apps default to a 1024 MiB total RAM budget, 512 MiB per web container, 256 MiB per worker/job, a maximum of one CPU core and normal CPU priority. These defaults need no manual rebalance for normal deployment. Optional overrides are under Advanced on the new-application and Resources pages. Only administrators can change resource budgets and server reservations; deployers and viewers can read measurements.

The RAM budget must cover **two web containers plus every enabled worker/job**. This bounds the app's aggregate process limits during rollout/rollback even when a scheduled command is currently idle; automatic mode does not reserve that entire ceiling as physical RAM. A new worker that exceeds the reservation is rejected before altering the existing task. Launches also account for live/orphaned app containers and concurrent launch reservations. Memory caps are fixed per process and enforced by Docker; their sum cannot exceed the app budget. They are not reduced as another app or worker is added. Saving a lower limit requires a fresh measurement below 90% of the proposed limit. Swap allowance is bounded to the process RAM cap in addition to its physical RAM cap.

Each app has one CPU allocation. In automatic mode, running/launching normal-priority apps get equal shares of the available pool, subject to their requested maximums. Lower/higher priority have half/double weights. The allocation is divided across that app's running web copies and workers, so adding workers does not increase its share. Ceilings scale when total demand exceeds the available CPU pool and are rounded down to hundredths of a core. Applied limits remain visible separately from requested limits. A dedicated root cgroup is not required: admission plus individual hard limits enforce the aggregate budget across containers owned by the agent.

Legacy apps preserve their existing web and worker RAM caps; their app ceiling includes enabled workers. Resource metadata persists in encrypted agent state. Existing policies with no memory mode automatically use live-capacity admission after the agent upgrade. Explicitly saved limits are preserved. In strict mode, existing apps keep running if maximum reservations exceed RAM, but new launches/builds are blocked; reducing reservations to repair that strict overcommit is allowed incrementally.

## Host headroom, services and builds

Automatic defaults protect host headroom (about 20% of physical RAM, rounded down to 128 MiB, at least 512 MiB) and a 512 MiB operational pool. The default build cap adapts to about one quarter of host RAM, rounded up to 128 MiB, between 1024 and 4096 MiB: about 2048 MiB on an 8 GiB host. It is deducted for active/starting builds, not permanently reserved while idle. CPU headroom is about one eighth of the cores, with bounded build and operational CPU allocations. Saved explicit limits are unchanged by hardware resizing; unsaved defaults follow host capacity. Only strict mode requires all maximum reservations to fit physical RAM.

Managed PostgreSQL defaults to 1024 MiB and a 0.5-core requested ceiling; Valkey defaults to 256 MiB and a 0.5-core requested ceiling. Managed ClickHouse defaults to 2048 MiB and a one-core requested ceiling (minimum 1024 MiB). Its persistent service is included alongside PostgreSQL and Valkey. Their CPU ceilings are adjusted alongside apps. Service limits can be edited on the server resource page; the minimum is 256 MiB. These are process limits and do not change PostgreSQL buffers or Valkey's configured cache size. Current usage is checked before a reduction. Overrides survive service restarts/provisioning. Shared/retained service containers are accounted once, and external containers are included in live host memory usage. Strict mode counts their configured maximums as reservations.

Builds use a dedicated **Docker Buildx container driver**, isolated from the operator's default builder. Its memory and CPU quotas constrain compiler child processes as well as BuildKit. It is stopped when idle; build cache remains available. Docker Buildx and kernel CPU quota, CPU shares and memory controllers are required. Missing controllers prevent launches rather than silently claiming enforcement. A build that genuinely needs more RAM requires a larger build reservation and enough remaining host capacity.

Backups, restores and database-size checks share the bounded operational RAM pool. Commands wait for a slot and cancel with their request context. Their CPU limits are proportional to their fixed RAM reservations, so simultaneous helpers cannot exceed the pool. Scoped orphaned helpers are removed after agent restart before retrying interrupted work. Other small provisioning helpers remain covered by host headroom and their existing individual memory caps.

After activation, an idle previous web release is stopped but retained for rollback. Rollback reserves resources, starts the previous image, waits for readiness and only then switches routing. A failed candidate or failed rollback retains the live release. App limits account for the old live image and candidate concurrently; automatic admission also accounts for pending launches against live memory.

## Alerts and validation

Configure SMTP in Integrations to receive durable alerts and recoveries. The operational tick checks once a minute: memory near an app or container ceiling for three checks, CPU near its allocated ceiling for five checks, repeated container restarts for two checks, and OOM/host capacity shortage at the first check. In automatic mode, capacity alerts refer to actual available headroom; in strict mode they refer to reservation overcommit. A missing measurement is not treated as healthy or as zero. Resource incidents survive control-panel restart and are removed when an app is removed.

Validation includes the 11776 MiB-ceiling/7941 MiB-host regression with sufficient live RAM, automatic wait/recovery/cancellation, default adoption for older policies, idle app/build accounting, a real bounded build and web deployment with oversized unused ceilings, weighted allocation fuzzing, migration/restart durability, memory/CPU accounting, helper pool concurrency, both Docker CPU-controller formats, real BuildKit builds, two-app deployment/redeployment/rollback, a CPU-bound worker and a deliberate cgroup OOM that leaves the web app serving. Browser checks cover mobile/desktop resource pages, writes, permissions, direct links, offline retention, persistent action errors, stable rows, drafts, focus and scroll. Run `npm run test:resources --prefix tests/browser` with `TEST_WEB_URL`, and `TEST_DOCKER=1 go test -race ./internal/agent -run 'DockerAppResource|DockerTwoApps'` for kernel/container checks.
