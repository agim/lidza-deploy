# Application resources and server capacity

Open **Application → Resources** for CPU/RAM usage, effective container limits, restart counts, OOM state and the app's budget. **Servers → Manage server → Resources** shows all apps, shared services and server reservations. The Server health link also opens this page. Resource readings refresh about every ten seconds. Missing readings display Unavailable; interrupted connections retain the previous readings and show an error. Forms, row identities, focus and scroll remain stable during polling.

CPU 100% means one core, not the entire server. RAM usage is Docker's working-set measurement; file cache and swap are not included. Database sizes on Server health are disk sizes, not RAM. Shared databases/cache containers are listed separately and counted once. Retained services continue to reserve memory while running. Non-Lidza containers are reported but not controlled. Unbounded external workloads require sufficient host headroom; the agent cannot guarantee the behavior of software outside its ownership.

## App budgets

New apps default to a 1024 MiB total RAM budget, 512 MiB per web container, 256 MiB per worker/job, a maximum of one CPU core and normal CPU priority. These values can be set on the new application page or changed later in Resources. Only administrators can change resource budgets and server reservations; deployers and viewers can read measurements.

The RAM budget must cover **two web containers plus every enabled worker/job**. This reserves rollout/rollback headroom even when a scheduled command is currently idle. A new worker that exceeds the reservation is rejected before altering the existing task. Launches also account for live/orphaned app containers and concurrent launch reservations. Memory caps are fixed per process and enforced by Docker; their sum cannot exceed the app budget. They are not reduced as another app or worker is added. Saving a lower limit requires a fresh measurement below 90% of the proposed limit. Swap allowance is bounded to the process RAM cap in addition to its physical RAM cap.

Each app has one CPU allocation. Normal-priority apps get equal shares of the available pool, subject to their requested maximums. Lower/higher priority have half/double weights. The allocation is divided across that app's running web copies and workers, so adding workers does not increase its share. Ceilings scale when total demand exceeds the available CPU pool and are rounded down to hundredths of a core. Applied limits remain visible separately from requested limits. A dedicated root cgroup is not required: admission plus individual hard limits enforce the aggregate budget across containers owned by the agent.

Legacy apps preserve their existing web and worker RAM caps on migration; their total reservation includes enabled workers. Resource metadata persists in encrypted agent state. Docker-backed agents reconcile existing containers periodically. If reservations exceed physical RAM, existing apps continue running with CPU fairness reconciled, new launches/builds are blocked, and resource pages show the shortfall. Reducing reservations to repair an existing overcommit is allowed incrementally. No automatic memory reduction is used to force a fleet to fit.

## Host, service and build reservations

The server plan reserves host headroom (about 20% of physical RAM, rounded down to 128 MiB, at least 512 MiB), a 1024 MiB build pool and a 512 MiB operational pool. CPU headroom is about one eighth of the cores, with separate bounded build and operational CPU allocations. All RAM reservations must fit physical RAM, irrespective of current low utilization. Changing hardware does not create additional memory inside already-configured budgets; review the server plan after resizing.

Managed PostgreSQL defaults to 1024 MiB and a 0.5-core requested ceiling; Valkey defaults to 256 MiB and a 0.5-core requested ceiling. Their CPU ceilings are adjusted alongside apps. Service limits can be edited on the server resource page; the minimum is 256 MiB. These are process limits and do not change PostgreSQL buffers or Valkey's configured cache size. Current usage is checked before a reduction. Overrides survive service restarts/provisioning. Shared/retained service containers are accounted once, and active bounded external containers reserve their configured memory limits.

Builds use a dedicated **Docker Buildx container driver**, isolated from the operator's default builder. Its memory and CPU quotas constrain compiler child processes as well as BuildKit. It is stopped when idle; build cache remains available. Docker Buildx and kernel CPU quota, CPU shares and memory controllers are required. Missing controllers prevent launches rather than silently claiming enforcement. A build that genuinely needs more RAM requires a larger build reservation and enough remaining host capacity.

Backups, restores and database-size checks share the bounded operational RAM pool. Commands wait for a slot and cancel with their request context. Their CPU limits are proportional to their fixed RAM reservations, so simultaneous helpers cannot exceed the pool. Scoped orphaned helpers are removed after agent restart before retrying interrupted work. Other small provisioning helpers remain covered by host headroom and their existing individual memory caps.

After activation, an idle previous web release is stopped but retained for rollback. Rollback reserves resources, starts the previous image, waits for readiness and only then switches routing. A failed candidate or failed rollback retains the live release. Budgets account for the old live image and candidate concurrently.

## Alerts and validation

Configure SMTP in Integrations to receive durable alerts and recoveries. The operational tick checks once a minute: memory near an app or container ceiling for three checks, CPU near its allocated ceiling for five checks, repeated container restarts for two checks, and OOM/host reservation overcommit at the first check. A missing measurement is not treated as healthy or as zero. Resource incidents survive control-panel restart and are removed when an app is removed.

Validation includes weighted allocation fuzzing, migration/restart durability, memory/CPU accounting, helper pool concurrency, both Docker CPU-controller formats, real BuildKit builds, two-app deployment/redeployment/rollback, a CPU-bound worker and a deliberate cgroup OOM that leaves the web app serving. Browser checks cover mobile/desktop resource pages, writes, permissions, direct links, offline retention, persistent action errors, stable rows, drafts, focus and scroll. Run `npm run test:resources --prefix tests/browser` with `TEST_WEB_URL`, and `TEST_DOCKER=1 go test -race ./internal/agent -run 'DockerAppResource|DockerTwoApps'` for kernel/container checks.
