# App domains and automatic HTTPS

On the first successful deployment, and when a running app's FQDN is edited, the hosting agent checks DNS immediately. Pending DNS/HTTPS checks retry about every **10 seconds after the previous attempt finishes**. Ready domains are rechecked every five minutes. Each domain has its own retry clock, so a slow check does not hold up other domains; work is bounded to eight domains at once. Edited/removed domains cancel their old checks. Cached DNS answers and slow network/certificate checks can still delay results. The GUI normally refreshes about every five seconds and displays the failure message separately below the hostname, with the hosting agent's retry timing. Older agents continue reporting their previous one-minute retry interval until upgraded. Point the domain's A record to the hosting server's public IPv4 address. If AAAA records also exist, every IPv6 address must reach the same hosting server. Remove obsolete addresses. The GUI shows **Waiting for DNS**, **Requesting SSL**, or **HTTPS ready**.

The agent resolves the domain with a five-second lookup budget and checks addresses concurrently (up to four at once) over HTTP using its own fresh domain-specific verification response. Every address must pass; a redirect, wrong proof or unavailable address still blocks issuance. Errors identify the failing IP/port and whether the connection timed out, was refused or was unreachable. This verifies the hosting server even when its public IP is mapped through NAT. The installer adds `/.well-known/lidza-deploy-host` to Caddy's HTTP listener; normal HTTP requests redirect to HTTPS. Public TCP ports 80 and 443 must reach Caddy, and the hosting server must be able to reach its own public addresses. DNS must serve the hosting server directly rather than an unrelated proxy/CDN endpoint that redirects, caches or rewrites the verification route.

Once all addresses are verified, the agent initiates an HTTPS connection to local Caddy with the app's FQDN as SNI. Caddy obtains the certificate before any visitor is needed. The agent verifies the trusted certificate and hostname before reporting HTTPS ready. Caddy handles automatic renewal. Issuance failures remain pending and retry; deployment can finish while DNS propagates. An edited FQDN follows the existing automatic runtime reload behavior.

Caddy's issuance authorization also verifies DNS afresh, so stale DNS status cannot authorize a new certificate. Removed and previous domains lose authorization. The worker resumes after agent restarts and continuously rechecks deployed apps. `tls_listen` in the agent config defaults to `127.0.0.1:443`; set it to the local TLS listener if you use a custom port. An explicit empty value disables this worker for an isolated development agent without Caddy.

Existing installations need the updated agent and the installer's updated Caddy configuration. Run the installer upgrade using the original required GUI `--fqdn` and any agent hostname options. If you maintain Caddy manually, add the HTTP verification route shown in `scripts/install-agent.sh` and reload Caddy. There is no need to change DNS for an already correct domain.

## Error and maintenance pages behind an existing Caddy

When the host's web ports belong to an existing Caddy configured through its admin API (see **Servers → Web ingress**), the agent keeps neutral, self-contained pages in `/etc/lidza/pages`: `error.html` ("This site is temporarily unavailable…") and `maintenance.html` ("Down for maintenance…"). They have no external assets, follow the visitor's light or dark preference, and are written idempotently at startup and whenever an application is published. The directory is root-owned with mode 0755 and the pages 0644, so Caddy can read them under its own account while only root can change them.

Each created application published to that Caddy also gets an error route for its hostnames (`@id` `lidza-errors-<app>`): a 503 is answered with `maintenance.html`, any other error with `<status>.html` when present, else `error.html`. Created applications whose processes do not answer get the same error page from the agent proxy.

If existing error routes serve pages from another directory (for example one that no longer exists), **Web ingress** reports how many hostnames are affected and offers **Use Līdza error pages**. It rewrites only those error-page roots to `/etc/lidza/pages`, loads the modified configuration through the admin API (`POST /load`) and verifies the result.
