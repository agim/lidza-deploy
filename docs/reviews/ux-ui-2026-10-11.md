# Līdza Deploy UX/UI review — October 11, 2026

## Verdict and scope

The product has working orchestration flows but does not yet have a coherent
interaction and layout system. Moving a dialog into the workspace is insufficient:
legacy CSS, duplicate headers, unrelated global actions and ambiguous status
messages survive the move. These are product defects, not a palette problem.
Keep the approved dark/pink Līdza palette.

Reviewed source, the supplied production screenshots, browser screenshots of 23
workspace routes at 390×900 and 1440×900, and relevant interaction tests. Included
applications, deployments, servers, databases, integrations, defaults, updates,
team, audit, errors, security, help, creation, settings, build/runtime logs,
database management, tasks, previews, cache, SSH, upgrades and server editing.
Login and setup were also examined through existing source and browser tests.
Browser route audit used demo data; it does not validate real provider delivery,
production secrets, ACME, remote agents or every populated/permission state.
Automated geometry checks are evidence, not a substitute for visual review.

## Shared rules

- Full pages for forms, logs, histories and multi-step work. Small dialogs only
  for short summaries and explicit confirmations.
- One visible page title, a meaningful parent breadcrumb and a text Back action.
- Page content aligns with the workspace heading. Forms use document scrolling.
  Bounded scrollers are appropriate for logs and search suggestions.
- One visually dominant action per task; secondary actions share sizing and gaps.
  Links navigate; buttons perform actions. Downloads may use link semantics but
  must have the same action styling and touch target as adjacent buttons.
- Saving, saved, failed, queued, running and completed are separate states.
  A connection test is not proof of an uploaded backup or delivered email.
- Never replace a focused input, reorder rows arbitrarily, hide old data while
  refreshing, reset reading position or discard edits without an explicit choice.
- Success notices expire after eight seconds, pausing for hover/focus. Actionable
  errors persist until dismissed or superseded. Feedback belongs near its task;
  dialog feedback must be inside the native dialog's top layer.
- Keep secrets write-only; show credential presence and validation state without
  exposing stored values. Preserve OAuth and permission checks.

## Evidence and validation

After shared CSS corrections, 46 demo route/viewport combinations reported no
horizontal document overflow, nested workspace form scrollers or displayed load
failures. Screenshots were captured for visual inspection. These checks do not
assert that every design choice is good or that every possible content length fits.

Relevant browser checks passed during this work: creation, settings customer-host
opt-in, full-page settings/build/runtime log routes and reloads, draft guard,
refresh position, Help links, defaults, cache local/external attachment, SSH keys
and viewer permissions, clipboard/download fidelity, live-log pause/reconnect/
completion/cleanup, storage status, notifications and setup error persistence.
Error-detail and upgrade/restore direct-route demo checks also passed.
Webapp tests and JavaScript syntax/diff checks passed. Release workflows run
source tests/race/vet and package/checksum/version verification for both binary
architectures. No production S3 backup upload or SMTP delivery was performed by
this review.

## Remaining review matrix and sequence

1. Validate populated databases and backup histories at both widths, including
   long object names, failed uploads, pending operations and external databases.
   Confirm one rolling predeployment copy remains independent of retention.
2. Rebuild app settings and database pages around shared section/card/action
   components. Review side-by-side screenshots before declaring visual completion.
3. Consolidate selectors, environment actions, parent navigation and breadcrumbs.
4. Test keyboard-only use, visible focus, tab order, screen-reader announcements,
   200% zoom, long app/repo names and measured contrast.
5. Exercise disconnected agents, OAuth denial/pending registration, wrong storage
   credentials, upload failure, SMTP failure, busy/failed updates and role changes.
6. Verify real provider flows in an authorized test environment: upload, download,
   checksum, restore, email delivery and certificate routing. Do not use production
   secrets in demo screenshots or treat mocked browser success as provider proof.

Reusable missing framework capabilities must be checked against the released
framework and raised upstream before a local substitute is built. Layout,
navigation, product-specific status presentation and action hierarchy belong in
Deploy. The defects fixed here do not require a framework issue.
